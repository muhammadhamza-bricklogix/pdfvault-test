# PDF editor — architecture & gotchas

This editor lets users open a PDF, edit text/shapes/images on top of it, manage pages (reorder, rotate, duplicate, color, bg image, watermark), and save back. The pipeline is intricate; this skill is the orientation map.

## Pipeline (load → edit → save)

```
File / cloud doc
        │
        ▼
usePdfLoader        — loads pdf.js doc + sets `pdfDocument` in the Zustand store
        │
        ▼
usePageRenderer     — renders the CURRENT page to a <canvas> via pdf.js
                      (scale = zoom × dpr; suppressText: true)
        │
        ▼
useFabricCanvas     — overlays a Fabric.js canvas at the same CSS size
                      (enableRetinaScaling: true; setZoom(zoom))
        │
        ▼
useEditTextMode     — extractTextBlocks → FabricIText objects per text run
                      (fonts come from pdf.js's loadedName via document.fonts)
        │
        ▼
Per-tool hooks      — draw / highlight / shape / image / signature / watermark
                      (each tool layers Fabric objects onto the overlay)
        │
        ▼
Save paths:
  • Editor "Save" → use-save-editor → persistEditorDocument
        → save-utils.buildEditedPdfBytes → merge-pdf.mergeFabricEditsIntoPdf
        → cloud upload
  • Manage Pages "Save" → handleManagePagesSave in PdfEditorShell
        → build-pages-pdf.buildPdfFromDraft
        → new File replaces the editor's source
  • Export PDF → window event "editor:export" → use-export-editor
```

## Load-bearing invariants (do not violate)

1. **Fabric uses base coordinates at zoom = 1.** `use-fabric-canvas.ts` keeps the Fabric canvas at base dims and applies `setZoom(zoom)` on top. **Serialized JSON is always in base coords.** Anything reading/writing Fabric JSON must assume zoom=1.

2. **Zoom changes only resize Fabric, never re-mount.** Mount effect runs only on `sourcePage` change; a separate effect calls `setDimensions + setZoom + obj.dirty = true + renderAll`. Don't add `renderedSize` to the mount effect's deps — that brings the cluttered-text + blur regression back.

3. **Page rotation is BAKED INTO THE CONTENT STREAM, never `/Rotate` metadata.** `append-pdf-page.ts` uses `embedPage` + `concatTransformationMatrix` for source/imported pages; `appendColoredPageFromPdfJs` passes `rotation` to `getViewport`; blank pages swap W/H. **Never call `page.setRotation(degrees(...))` for manage-pages output** — it ships `/Rotate` metadata which makes text positions desync from the rendered layout in the editor.

4. **Text colors flow: pdf.js OPS → `TextBlock.color` → Fabric `fill` → `hexToPdfColor` at export.** `extractSequentialTextColors` walks the operator list; colors are zipped 1:1 to text items by index (mode-color fallback if counts mismatch). Re-arrange this only if you understand the index-correlation issue.

5. **Background image preview uses `mix-blend-mode: multiply` on the PDF canvas.** Not on the Fabric overlay. The img element sits as a sibling before the canvas; canvas with multiply burns white through to image. At export it's the same trick via `BlendMode.Multiply` on `drawImage` in `merge-pdf` / `build-pages-pdf`.

6. **Background color (per-page, from Manage Pages) is baked at manage-pages save.** Stored on `DraftPage.backgroundColor`, applied by `buildPdfFromDraft` via `appendColoredPageFromPdfJs`. After save the color is part of the source PDF — no extra state survives.

7. **Mobile rendering**: `RightSidebar` isn't mounted on mobile. Watermark + background-image config render via `MobileToolPropertiesModal` mounted inside `BottomDock`. Closing the modal sets `activeTool = "select"`.

   **Text editing is tool-gated for everyone (mobile + desktop).** Default state on every page: pdf.js paints text natively (`suppressText` is driven by `extractedPages.has(sourcePage)` in `PdfViewerCanvas.tsx`). When the user activates the **"Edit Text" toolbar tool** (`activeTool === "editText"`), `useEditTextMode` runs extraction for the current page, places Fabric IText objects, and calls `markPageExtracted(sourcePage)` — only then does `suppressText` flip on so pdf.js stops painting text under the overlay. IText survives tool switches: once extracted, the page stays in overlay mode (tap any sentence to edit) regardless of which tool is currently selected. If `extractTextBlocks` throws (older iOS Safari WebKit on `getTextContent`), the hook reverts `activeTool` back to "select" and toasts the user — the page never flips `suppressText` on, so native pdf.js text keeps painting and the page stays readable.

8. **All runtime pdfjs imports go through `loadPdfJs()`** (`lib/client/pdf-editor/load-pdfjs.ts`), which installs `Promise.withResolvers` / `Object.hasOwn` / `structuredClone` polyfills before importing the **legacy** pdf.js build. Direct `import("pdfjs-dist")` or `import("pdfjs-dist/build/...")` skips the polyfills and may break on older Safari.

9. **TypeScript target is ES2022** (`tsconfig.json`). Don't drop it back to ES5 — bumping killed all the down-leveling polyfill weight and resolved a long tail of TS2802 errors.

10. **Editor modals are lazy.** `CreatePdfModal`, `ManagePagesModal`, `PerformancePanel` are loaded via `next/dynamic` and conditionally mounted. Don't import them statically into `PdfEditorShell.tsx`.

11. **Save UX must always show a loading toast.** `useSaveEditor` and `useEditorNavigationSave` both open `toast.loading(...)` before `persistEditorDocument` and close it in `finally`. The cloud upload is multi-second — silent waits look like a hang.

## Hot spots / fragile areas

- **`lib/client/pdf-editor/text-extraction.ts`** — color-to-item mapping zips by index. If `colors.length !== textContent.items.length`, falls back to mode color (when uniform) or black. Won't be perfectly correct for documents with mid-paragraph color changes plus split text items.
- **`lib/client/pdf-editor/merge-pdf.ts`** — has its OWN inline copy of `renderPageToPng` + `TEXT_OPS_MIN/MAX/RASTER_SCALE`. The shared `render-page-png.ts` is used only by `build-pages-pdf.ts`. Do NOT consolidate them; the user explicitly asked to keep `merge-pdf` undisturbed.
- **`use-fabric-canvas.ts`** — refs `renderedSizeRef`/`zoomRef` exist specifically so the mount effect doesn't re-run on zoom. Don't accidentally inline these back into deps.
- **`use-edit-text-mode.ts`** — `objectCaching: false` is set on every IText. The user reverted an attempt to enable caching; leave it off.
- **`build-pages-pdf.ts`** — for imported PDFs with bg color, pdf.js docs are lazy-loaded and cached per `importKey`. Same cache approach is needed if you add other pdf.js-driven per-page work.
- **`use-fabric-canvas.ts` (mobile-touch trio)** — three values stay coupled per active tool: `fc.allowTouchScrolling`, `fc.upperCanvasEl.style.touchAction`, `wrapper.style.touchAction`. Drawing tools = `false / "none" / "none"`; everything else = `true / "pan-x pan-y" / "pan-x pan-y"`. Wrapper-only changes don't work because the upper-canvas overlays it; allowTouchScrolling alone doesn't work because Fabric's constructor-time `touch-action` value is sticky. See 2026-06-10 (e).
- **`PdfViewerCanvas.tsx` scroll container** — uses the `mx-auto w-fit` pattern, **not** `flex justify-center`. Flex centring on an overflowing child traps iOS Safari users at the centre of a zoomed page (can't reach left/top edge). See 2026-06-10 (e).
- **`HamburgerMenu.tsx` ↔ shell hooks** — any tool that consumes the user's **edited** bytes (Export, Extract Images, anything similar) must live in `PdfEditorShell` next to `useExportEditor` so it has the live `fabricCanvas` ref. `HamburgerMenu` only **dispatches** events (e.g. `editor:extract-images`); it must never `mutateAsync({ file: store.file })` for tools that operate on edits, because `store.file` is the original upload until the next Save. See 2026-06-10 (f).

## Load-bearing invariants (verify before changing)

As of 2026-08-27 the lock hook enforces only the tightest subset (see `.claude/LOCKED_PATHS`). Everything below is still load-bearing — every entry fixes a specific user-reported regression — but the enforcement mode is "verify with the invariants list in CLAUDE.md and the decisions log below, then edit carefully" instead of "ask before unlocking".

- The `hasGenuineEdits` guard at the top of the per-page loop in `merge-pdf.ts`. Falling back to Case 1/2 for pages whose overlays are only auto-extracted IText (`editorType === "editModeText"`) is what keeps text selectable on export / share / extract-images. See 2026-06-15 (c).
- The inline `renderPageToPng` function + the `TEXT_OPS_MIN`, `TEXT_OPS_MAX`, `RASTER_SCALE` constants in `merge-pdf.ts`. A shared util exists for `build-pages-pdf.ts` — do not consolidate them.
- The watermark code in `merge-pdf.ts` (authored by another dev; reverting their structure has burned cycles before).
- `objectCaching: false` on IText in `use-edit-text-mode.ts`.
- The mobile-touch trio in `use-fabric-canvas.ts` (allowTouchScrolling + upper-canvas touch-action + wrapper touch-action, coupled per active tool). Reverting any one of these to the pre-2026-06-10 (e) state freezes 1-finger pan when zoomed in on iOS Safari.
- The `mx-auto w-fit` scroll-container pattern in `PdfViewerCanvas.tsx`. Don't replace with `flex justify-center` — same iOS Safari freeze.
- The shell-level `useExtractImagesEditor` hook + `editor:extract-images` event indirection. Don't fold it back into `HamburgerMenu` — that re-introduces the "backend sees original upload, not edits" bug (2026-06-10 (f)).
- `PdfViewerCanvas.tsx` fit-to-width caps at `MAX_ZOOM = 1.0`. Browser zoom-out inflates `clientWidth`; an uncapped fit result exceeds the toolbar's 2.0 preset and locks the `+` button. See 2026-08-19.
- `ToolToolbar` in `PvEditorTopChrome.tsx` uses `flex-wrap justify-center`, NOT `w-fit`. Desktop-only container — no iOS Safari trap here — but `w-fit` prevents wrap and pushes tools off-screen at higher browser zoom. See 2026-08-19.

If a fix requires changing one of these, still surface it before pushing — the user has revised prior calls when UX breaks (see `feedback_off_limits_revisable` memory), but wants the reasoning stated.

## Verification recipe

After any non-trivial PDF editor change, run:

```bash
bunx tsc --noEmit                          # type check
bun run lint                                # eslint
bun run build                               # full Next build (catches use-server/use-client mismatches)
```

Then manually verify in `bun run dev`:

1. Open a multi-page PDF → text editing still works on first page.
2. Zoom in to 200% and out to 50% → text stays sharp + positioned.
3. Manage Pages → rotate one page 90° → save → that page reads correctly (no cluttered text).
4. Manage Pages → set background color on a source page → save → color visible behind content.
5. Watermark tool → add text watermark → preview matches export.
6. Background image tool → upload → preview shows behind page; export matches.
7. Save (cloud) → loading toast appears → success toast on completion.
8. Mobile viewport → watermark / bg image tools open the modal.

- **2026-09-10 — Flatten and Compress tools lost all editor edits in downloaded PDF (BAKE-BEFORE-TOOL FIX).** QA report: open PDF in Composer → add text/draw/highlight/sign → use Flatten or Compress → downloaded PDF shows original content, all edits gone. **Root cause:** `HamburgerMenu.runFlatten()` called `useFlattenFileMutation.mutateAsync({ file: store.file })` directly — `store.file` is the original upload bytes until an explicit Save bakes Fabric overlays into it. Compress had the same bug: `CompressModal.handleCompress()` passed `store.file` to `compress.mutateAsync`. Neither tool had access to the live `fabricCanvas` ref (that ref only exists in `PdfEditorShell`), so neither could call `buildEditedPdfBytes` to bake overlays. **Root-cause class:** identical to the Extract Images bug fixed 2026-06-10 (f) — tools that consume "the user's edited bytes" must live at shell level (or dispatch to shell) because only `PdfEditorShell` holds the live `fabricCanvas` ref. **Fix (flatten):** created `lib/client/hooks/pdf-editor/use-flatten-editor.ts` — shell-level hook (same pattern as `use-extract-images-editor.ts`) that listens for `editor:flatten`, calls `buildEditedPdfBytes({ bakeOverlays: true, fabricCanvas, ... })` to bake Fabric overlays client-side, wraps the baked bytes in a `File`, then calls `useFlattenFileMutation`. Mounted in `PdfEditorShell` next to `useExtractImagesEditor`. `HamburgerMenu.runFlatten()` simplified to `window.dispatchEvent(new CustomEvent("editor:flatten"))` — dispatches and returns; all auth/paywall/bake logic moved to the shell hook. **Fix (compress):** `CompressModal.handleCompress()` dispatches `editor:build-current-bytes` with `bakeOverlays: true` (new field added to the event detail type in `use-save-editor.ts`) and awaits the baked `Uint8Array` via the onComplete callback before calling `compress.mutateAsync`. Falls back to `store.file` if the event resolves null (editor not mounted). The modal retains its own loading/close state because the TanStack Query mutation still lives there. **Load-bearing rule added:** Flatten and Compress MUST bake Fabric overlays before sending bytes to the backend. Do NOT revert `HamburgerMenu.runFlatten` to call the mutation directly — that path uses `store.file` (original bytes) and loses all in-session edits. Do NOT remove the `bakeOverlays: true` flag from `CompressModal`'s `editor:build-current-bytes` dispatch. **Hydrator path unaffected:** `?tool=flatten` → hydrator dispatches `editor:open-flatten` → HamburgerMenu bridge → `runFlatten()` → `editor:flatten` event → shell hook. `?tool=compress` → hydrator opens modal → user clicks Compress → bake event. Both return paths still work. **Verified:** `bunx tsc --noEmit` clean (no new errors in touched files), `bunx eslint --fix` clean on all 5 touched files. **Files touched:** `lib/client/hooks/pdf-editor/use-flatten-editor.ts` (new), `lib/client/hooks/pdf-editor/use-save-editor.ts` (added `bakeOverlays` to event detail type + `buildEditedPdfBytes` call), `components/sections/pdf-editor/PdfEditorShell.tsx` (import + mount `useFlattenEditor`), `components/sections/pdf-editor/HamburgerMenu.tsx` (simplified `runFlatten`, removed `useFlattenFileMutation`/`requestPaywall`/`triggerBlobDownload`/`logger` imports), `components/sections/pdf-editor/CompressModal.tsx` (bake-before-compress via `editor:build-current-bytes`).

- **2026-09-09 (b) — Text placement drifts UP on download vs composer at large font sizes (BASELINE MATH FIX).** User report: Text tool → type "96" → set font size 96 + Bold + Italic → composer places the glyph at Y1, downloaded PDF places it ~15 pt higher at Y2. Reproduced with Edit-tool-modified extracted text too (change existing text to "96", crank fontSize to 96). **Root cause:** Fabric v6/v7 renders a Text/Textbox's line-0 baseline at `top + fontSize × _fontSizeMult × (1 − _fontSizeFraction) = top + fontSize × 1.13 × 0.778 = top + fontSize × 0.87914` (verified in `node_modules/fabric/dist/src/shapes/Text/Text.mjs:520-575` + `constants.min.mjs`). `drawIText` in `vector-drawers.ts` was placing the baseline at `top + font.heightAtSize(size, {descender:false})` which for Helvetica-family StandardFonts resolves to `top + fontSize × 0.718` (`Ascender/unitsPerEm = 718/1000`). Drift = `(0.87914 − 0.718) × fontSize = 0.161 × fontSize` → 15.5 pt at fontSize 96, 2-3 pt at fontSize 12-16 (below QA's detection floor for years). Direction: download drew HIGHER on the page than composer painted. **Fix (`lib/client/pdf-editor/vector-drawers.ts` only):** (1) added a module-level constant `FABRIC_BASELINE_MULT = 1.13 * (1 - 0.222) = 0.87914` with full derivation in the docstring, (2) replaced `ascendFabric = fontHeight / ctx.scaleY` with `ascendFabric = fontSize * FABRIC_BASELINE_MULT` for **all** text overlays that reach `drawIText`, (3) removed the now-unused `fontHeight` local. **Why safe for editModeText:** pristine editModeText never reaches this drawer — `merge-pdf.ts:isModifiedEditModeText` filters them out and the source PDF page is copied byte-for-byte (source baseline stays pdf.js-authoritative). Only modified editModeText flows through drawIText, and every one of them was ALREADY painted by Fabric in the composer — matching Fabric's math is exactly what the user wants. The `whiteoutSourceText` rect over the original source text absorbs the ~1-2 pt baseline shift at typical PDF sizes (11-14 pt) so no visual overlap. **First-pass attempt that was insufficient:** initial fix only switched the formula for `editorType !== "editModeText"`, leaving modified editModeText on the old (drifted) formula. User re-tested with the Edit tool + fontSize 96 flow → still drifted. Second pass (the final fix) removed the editorType branch entirely so ALL drawer-bound text uses Fabric's baseline math. **Collateral improvement**: annotations, page numbers, and signature text also had the same latent drift; they now render at composer position too. **Load-bearing rule added:** `drawIText` MUST use `fontSize * FABRIC_BASELINE_MULT` for baseline placement, NOT `heightAtSize`. If Fabric ever changes `_fontSizeMult` or `_fontSizeFraction` in `constants.min.mjs`, update the constant to match. **Verified:** `bunx tsc --noEmit`, `bunx eslint`, `bun run build` all clean. **Manual walk owed:** open PDF → Text tool → type "96" → set fontSize 96 + Bold + Italic → Done → Download → confirm vertical position matches composer; repeat via Edit tool on extracted text; check annotations / page numbers still land correctly at 12-16 pt (they'll be ~2 pt lower than before, which now matches composer).

- **2026-09-09 (a) — Font family / size / bold / italic / color / align pick in FloatingTextToolbar silently reverts on save+download (PRISTINE FLIP FIX).** User report: change font family (or any style) on an extracted PDF text run via the FloatingTextToolbar → composer paints the change → downloaded PDF shows the ORIGINAL family. **Root cause:** `FloatingTextToolbar.applyStyle` mutated the object via `obj.set(fabricPatch)` — a pure Fabric setter that does NOT emit `object:modified`. The `use-editor-history.ts:104-118` handler `dirtySourceText` only flips `editModeText.pristine → false` on `object:modified` / `text:changed` events. Without the event, `pristine` stayed `true`, so `merge-pdf.ts:isModifiedEditModeText` classified the page as unchanged → Case 1 (copy source page byte-for-byte, ORIGINAL font baked in). Editor saw the new font because Fabric's next render reads `obj.fontFamily` directly; download used the source bytes. Same class of bug applies to fontSize, bold, italic, color, and text alignment picks on extracted text — every FloatingTextToolbar change silently reverted on save/export for pages containing only pristine editModeText. QA hit it first via font-family because that swap is the most visually obvious. **Fix (`components/sections/pdf-editor/FloatingTextToolbar.tsx` only):** after `obj.set(fabricPatch)` + `renderAll`, added `fabricCanvas.fire("object:modified", { target: obj })`. This triggers the three listeners registered in `use-editor-history.ts:121-128`: (a) `snapshot` (pushes history + serializes to `fabricJsonByPage`), (b) `markDirtyOnEdit` (sets `hasUnsavedChanges`), (c) `dirtySourceText` (flips `pristine = false` for editModeText). Non-editModeText overlays (annotations, signatures, page numbers, watermark, text tool) are unaffected because `dirtySourceText` early-returns on `editorType !== "editModeText"`; the other two handlers are safe to fire because they already run for user drag/resize interactions on those object types. **Load-bearing rule added:** any code path that mutates a Fabric text object programmatically MUST fire `object:modified` afterwards, otherwise the pristine-based classification in `merge-pdf.ts` treats the change as "not there" and the source page is copied verbatim on export. Applies equally to any future style panel that touches editModeText via `obj.set()`. **Verified:** `bunx tsc --noEmit` clean, `eslint` clean on the touched file.

- **2026-09-07 — Draw / highlight strokes missing from downloaded + merged PDFs (LIVE-CANVAS RASTER FIX).** User report: "PDF edits are not reflected in downloaded or merged PDF." Reproduced with `PDFVault-receipt-2026-09-07-pdfvault.pdf` (Solidgate receipt, 1-page). User drew 1 freehand path + 1 highlight, clicked Done → Download PDF and Merge → Merge & Download. Downloaded files showed the original source only, no strokes. **Root cause: Fabric v7's `loadFromJSON` doesn't fully rehydrate freehand `path` objects (PencilBrush strokes from draw + highlight tools) onto a fresh offscreen Canvas.** The bake pipeline serialized the live canvas to JSON (`canvas.toJSON()`), then called `renderFabricJsonToPng` in `save-utils.ts` which created a fresh Canvas, called `loadFromJSON`, then `toDataURL`. The returned PNG was 110KB (looked healthy by size) but was **~99.6% transparent** — visually blank. Embedded into the PDF page, the page shows source content only. **Why the smoke was invisible for so long**: (a) `bytesDelta > 0` at every save (~30KB from the PNG embed), (b) `likelyBlank: false` (a size heuristic — a 612×792 alpha PNG has 100+ KB of header/zlib overhead even fully transparent), (c) `rasterQueued: 2, byType: {Path: 1, Path:highlight: 1}` (path objects reached the raster batch correctly). All bake diagnostics said "success"; the pixel-content check was missing. **How we found it**: added `nonTransparentPixels` + `pixelFillRatio` fields to the `EXPORT-DIAG: renderFabricJsonToPng` log by sampling every 8th pixel of the offscreen canvas alpha channel after `renderAll`. First test log showed `pixelFillRatio: 0.39%, nonTransparentPixels: 30 / 7623 sampled` — that's ~one thin stroke's worth of pixels for a doc that had both a wide yellow highlight and a diagonal black draw stroke visible on the live canvas. `trulyBlank: false` (some render happened) but `pixelFillRatio: 0.39` proved the render was near-empty. **Fix (`renderFabricSubsetToPng` + new `renderSubsetFromLiveCanvas` in `save-utils.ts`, plumbed through `merge-pdf.ts`):** for the current page (the one the live canvas is displaying), skip the offscreen re-render entirely. Instead use the LIVE editor canvas — it already has the strokes correctly painted (literally what the user sees on screen). Sequence: (1) capture original visibility per object + original zoom + viewport + physical canvas dimensions, (2) mark all non-target objects `visible = false` (so only the raster batch's objects render), (3) call `setDimensions({ width: parsedW, height: parsedH })` + `setZoom(1)` + `setViewportTransform([1,0,0,1,0,0])` so the export is at base coords, (4) `renderAll()` + `toDataURL({ format: "png", multiplier: 3 })`, (5) restore viewport → zoom → dimensions → visibility (reverse order matters), (6) return the data URL. Other pages (that the live canvas isn't currently showing) still use the offscreen JSON-based render — no regression there. **Plumbing**: added optional `liveFabricCanvas` + `liveCanvasPage` params to `MergePdfInput` → forwarded through `processPageObjects` → `flushRasterBatch` → `renderFabricSubsetToPng`. `buildEditedPdfBytes` in `save-utils.ts` passes `liveFabricCanvas: fabricCanvas, liveCanvasPage: currentPage` at the call site. **Load-bearing invariants added**: (a) NEVER remove `renderSubsetFromLiveCanvas` — the offscreen `loadFromJSON` path is broken for freehand paths on Fabric v7.3.1. (b) Do NOT drop the `setDimensions` step — if the user is zoomed anything other than 1.0, the live canvas's backing store is smaller than the base-coord scene and `toDataURL` clips to the smaller size, producing partial exports. (c) The `pixelFillRatio` diagnostic in `renderFabricJsonToPng` should stay — it's the only signal that distinguishes a healthy render from a Fabric-v7-blank render, and future upstream Fabric bugs of the same shape will surface here first. **Related dead-ends we chased before the pixel-content diagnostic (do not re-attempt these as fixes for this class of bug):** (i) `new Blob([bytes])` vs `[bytes.buffer as ArrayBuffer]` — real byte-view bug, but pdf-lib's `save()` returns byteOffset=0 so not triggered here (logs proved `mergedOffset: 0, mergedBufferLen: mergedLen`). Fix landed anyway as defence in depth (`use-export-editor.ts:83, 385, 414, 511, 578, 637`, `MergePdfModal.tsx`, `SplitPdfModal.tsx`). (ii) MediaBox non-(0,0) origin — real for Solidgate receipts, but user's receipt had `mediaBoxIsOffset: false` per the log. Fix landed anyway for other docs (`flushRasterBatch` in `merge-pdf.ts` uses `mediaBox.x/.y`). (iii) CropBox smaller than MediaBox — plausible but user's `cropIsSmaller: false, cropOriginDiffers: false`. Fix landed anyway (same location). (iv) `objectCaching = false + dirty = true + setCoords()` on loaded objects — partial workaround for the same Fabric bug, insufficient for freehand paths. **How to diagnose this class of bug in one round next time**: user reports "drawings missing from download" → look for `EXPORT-DIAG: renderFabricJsonToPng` in the console → check `pixelFillRatio`. If < 5%, it's this bug — the offscreen render silently failed. Confirm `renderSubsetFromLiveCanvas` is on the code path (look for `EXPORT-DIAG: rendered subset from LIVE canvas` log). If missing, deploy hasn't landed (staging deploy from `fix/merge-splt-save-issues` branch) or a code change bypassed it. **Adjacent UX change shipped in the same round**: `PvEditorTopChrome` + `EditorTopBar` Done button now dispatches `editor:save-before-action` (force + skipReset) BEFORE opening `ExportFormatModal` so the cloud always has the latest edits by the time the user picks a format. `MergePdfModal.handleMerge` does the same before its in-memory bake.
